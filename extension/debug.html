Emporika · provider harness

Runs inside the extension origin, so host permissions apply and CORS is bypassed — the same network path the service worker uses.

Costco's GRS search API is Kasada-guarded, so only a real browser session can reach it. If the buttons fail, the app reports Costco as unavailable rather than pretending there were no matches.

Target's Redsky host answers service-worker requests with an HTTP 435 PerimeterX challenge, so this provider issues the request from a real target.com page's main world, where Target's own sensor is running. It acquires your open target.com tab when there is one, else a minimised popup — you may see a tab appear briefly. What each outcome means: a 435 here means PerimeterX rejected this page context. Measured from a genuine target.com page in a real browser: seven attempts over twenty seconds, every one 435 — so retrying does not help and is not attempted. If your profile (with its own history and cookies) still gets 435, the only remaining route is a visible tab that navigates to /s/<query> and lets Target render the results, then reads them from the DOM. “page context could not be created” means the tab or window could not be acquired. A JSON response with prices means the path works and the loss is upstream in the bridge.

Superseded note (kept for context): Target used to be disabled in search/providers/availability.ts because a background fetch could never satisfy the challenge.
